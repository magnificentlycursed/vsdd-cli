## Summary

The toolkit enables and enforces VSDD for projects whose work is executed by AI agents under a human operator's direction. The product is an installed environment: context, constraints, and hooks wired into crosslink's seams, in which following the methodology is the easiest available path and deviation produces immediate, compiler-shaped feedback. The operator's session-start intent expands deterministically because the process is deterministic: the same project state and process spec produce the same next action from any competent cold agent.

Division of labor:
- **crosslink**: issues, dispatch (swarm), worktrees, gates, sessions, knowledge, and raw usage capture (harvest, context measurement). The contract chain lives here.
- **vsdd** (methodology layer): process spec, phase state, composition, domain prompts, generated agent context, hooks, and the cost layer — the build-time static price and the records-based insight engine, a reader over the harness-produced run records (amendment pending SO ratification, vsdd-cli #840). Installed into crosslink's seams (rules, skills, hook config, house style).
- **mdatron** (conformance engine): validates every methodology artifact, including the phase state file and route table, invoked at action time by hooks and at boundary time by gates. Methodology-agnostic per its boundary preamble (see References).
- **operator**: doctrine, scope, priorities, approval, and oracle authorship (acceptance criteria and manual tests). All other decisions belong to the process or the tooling.

## Behavioral contracts

Contracts are referenced by their exact heading names. Each contract states its normative content, then its falsification path, then the evidence that motivated it.

### Deterministic phase answer

"What phase are we in?" has exactly one correct answer, derivable by any cold agent at any time.

- The phase state is a written artifact in the project repo. The draft location is `.vsdd/state.yaml`; the phase-state-location open question decides the final store in Phase 1b. The contract's mechanics below hold for whichever store is chosen. Contents: current layer, current phase, open-findings pointer, last gate result, active composition, and the published marker once the first-publish promotion act writes it (the machine-readable publish-state the fix-lane falsifiers consult; operator amendment 2026-07-19).
- The state advances only at phase boundaries, by the agent, in the same commit as the boundary evidence. The state artifact's validation is vsdd's own — shape at read and write, and the consistency-against-evidence checks (a state claiming phase 2b requires a recorded red-gate result for the layer) in vsdd's integrity machinery: the write-path constraints, the snapshot-scoped checks, and the gates (the mdatron boundary ruling, operator-ratified 2026-07-22, vsdd-cli #739: mdatron's scope is the markdown estate, and the state file is not markdown).
- The state rides the crosslink session machinery: the phase pointer travels in crosslink session breadcrumbs and is re-injected on resume after compaction; `session start` surfaces phase status with the prior handoff; phase boundaries require handoff notes; each phase execution and each layer is a crosslink milestone, so tracker-side progress and the state corroborate each other and the phase-versus-milestone integrity query is well-defined from phase 1a onward.
- When the tracker is unreachable, the phase answer is computed from the state artifact alone and reported as degraded. Concurrency, mid-phase crash recovery, state-versus-tracker precedence, and bootstrap validation are decision criteria of the phase-state-location open question.

Falsification: two cold sessions given the same repo and tracker state answer differently (a spec defect, chargeable to the spec rather than the agents); a state artifact inconsistent with repo evidence surviving an mdatron check.

Evidence: session entry has depended on prose reconstruction since the suite era; two sessions could disagree about the project's position, and in the June cycles the flow's position was lost entirely (June-cycle records and the operator interview, in References).

### Directive reconciliation

Every mid-flow operator directive is classified before execution. The classifications: phase-4 routing (bind it — file the routing, name the target phase), spec amendment (amend the design doc, then act), recorded override (execute, record via `crosslink intervene`, state where the flow stands and the re-entry path), or increment entry (the work is an increment — a feature entering at phase 1a, or a defect fix entering the fix lane of Finding lifecycle in one place; the classification also states the split side per Recorded review dispatch — for a defect fix, the attended act ends at filing and the dispatch invocation, the grant itself, with implementation and reviews autonomous; for a feature, the design phases it enters run attended, and the split applies at each dispatch thereafter). (Classification set extended by operator amendment 2026-07-19, the defect-fix lane ruling; split side added by the 2026-07-20 attended/autonomous ruling.)

- The classification is stated to the operator at the moment of receipt. The statement includes the inferred scope: whether the operator's words are read as a specific instruction or as instances of a general rule.
- Silent execution of an unclassified directive is a named defect. The operator holds the authority to redirect; the agent holds the duty to say what the redirect does to the flow.
- Reconciliation includes a mechanization step drawn from the AI Engineer domain: when a crosslink or harness mechanism serves the directive (milestone, session, hook, skill, config), it is named and offered at classification time. The AI Engineer domain also owns the recurrence-to-structure duty: the second occurrence of an operator correction or struggle obliges a proposed mechanization.
- The classification duty is symmetric (operator amendment 2026-07-19): session-originated code-touching work — a defect fix the agent judges routine maintenance — carries the same classification duty as operator directives. Its statement-target is the finding issue: for self-originated work the classification is recorded in the finding issue at filing, before implementation — the filing is the receipt-moment analog, and the scope reading is the governed-set determination (in or out of the lane, stated with the reason). The lane's substance is stated in Finding lifecycle in one place (defect fixes are increments).

Falsification: a directive executed with no classification recorded in the tracker or session record; a recorded classification lacking the scope reading; a recorded increment-entry classification lacking its split-side statement; a directive served by an available crosslink mechanism with no mechanism named at classification; a second-occurrence correction with no proposed mechanization; a session-originated change to the governed set (defined in Finding lifecycle in one place) implemented with no recorded classification.

Evidence: the operator issued directives in the June cycles believing them to be phase-4 routing; the agent executed them without classification, the flow was orphaned, and 137 findings accumulated with 82 of them orphaned before the operator noticed. Scope drift has failed in both directions: single utterances became named schema concepts, and illustrative examples were wired as enumerated special cases (June-cycle records and the operator interview, in References).

### Phase exit by gate

A phase closes only when its exit gate passes. Gates are commands; `crosslink swarm gate` runs them, and their results are recorded in the state artifact and the tracker.

- Red Gate, mechanized: phase 2a closes only when the layer's test suite fails against the pre-implementation commit and the failing run is recorded. Phase 2b closes only when the same suite passes at HEAD. The gate performs the checkout and run; agent assertion plays no part.
- Phase 3 closes only at the stop signal (a round producing only hallucinated findings) with all round findings filed. Phase 4 closes only when the unrouted-findings query returns empty.
- Mutation floor: when the review config declares one (the thorough preset does), the mutation kill-ratio on changed code is a standing gate criterion.
- The red gate applies at fix scale (operator amendment 2026-07-19), mechanized like the layer gate: the gate performs the work and agent assertion plays no part. What the mechanism does differs by commit topology, and the gate defines it rather than assuming the layer shape: the finding issue records the baseline commit (for a single-commit fix, the fix commit's parent), names the defect's test(s), and declares the expected failure kinds — a declared set drawn from the enumeration, since a real defect's kind can vary by platform or run order (operator ruling 2026-07-21); the wrong-reason comparison's second operand is a required field, not an inference; the gate checks out the baseline, applies the defect's pin test to it — test application is the defined fix-scale mechanism, since a fix and its test may share a commit — runs the named test(s) in isolation for defect attribution, and requires red there and green at HEAD; the green half is two runs: the named tests in isolation, where green is the symmetric executed pass — the pin built, was collected, ran, and passed; a skipped, ignored, filtered, or not-collected pin is neither red nor green but its own recorded state satisfying neither half — and the standing suite (the repo's declared test command at workspace scope, the same command the crosslink's gate resolves; cross-repo consumers are their own repos' gates) as a delta: the suite runs at baseline and HEAD and the gate compares by runner-reported test path, joining through the declared path mapping when the fix must relocate tests (the mapping is stated in the commit's structured evidence section — relocation-as-fix has a lawful lane, since inline test modules rename by construction when modules move; mappings are set-valued between paths vanished at HEAD and paths new at HEAD — splits and merges are lawful forms, a path appears in at most one mapping per side, and every target of a split inherits the dormancy scrutiny, so no split target escapes it (operator ruling 2026-07-21) — and carry validator approval exactly as deletions do — the approval record enumerates every pair and the gate checks the approved set equals the declared set, one recorded act with per-pair content, mechanical at any scale, so routing a deletion through a mapping buys no validator escape, a fresh passing decoy faces the validator who asks what each pair relocates, and a decoy buried in a bulk table is still a row the record names; no new-at-HEAD test may fail, while a skipped or ignored new test is neither pass nor fail per the pin doctrine's own vocabulary, so a genuinely failing relocation cannot slip by unmatched; a genuinely new test added ignored (no baseline history) blocks nothing, but a mapped target that arrives reported-but-non-executing at HEAD is the dormancy of an existing catcher — the scrutinies compose, and the mapping's record carries the disablement declaration for that pair, so relocation buys no escape from dormancy approval (adopted default, overridable at the phase-1c mapping schema: mapping targets are the report set, so a cfg-vanished target — absent from the runner report — cannot be a mapping target, and that relocation degrades to a source-path disablement with the relocation linkage a validator-trust item; a 1c decision for the source set would legalize such targets and retire the degradation); and a test that passed at baseline and is skipped, ignored, or not collected at HEAD is removal-shaped regardless of its path surviving — it takes its declared, validator-approved lane or fails the delta, so an in-place quarantine cannot hide a baseline-passing regression catcher); a fix that removes an obsolete passing test declares the deletion — path and reason, validator-approved — as its lawful form; a fix that leaves a still-valid test dormant (a feature-default flip, a runtime skip) declares the disablement — path, reason, validator approval — the third removal-shaped lane, keyed on intent alone: it covers the dormant test whether its path survives the runner report (a runtime skip) or vanishes from collection (a cfg-gated flip), and the join treats a declared-disabled vanished path as explained; the three lanes partition the removal-shaped set by intent — gone-and-obsolete is deletion, relocated is mapping, dormant-but-valid is disablement — with each affected path assigned exactly one primary lane and one stated mechanical exception: a relocation whose target the runner cannot report takes the disablement lane, because the report is the join's universe; a mapped pair whose target arrives non-executing additionally carries the disablement scrutiny on the same record, an attached approval, never a second lane claim; the gate runs baseline and HEAD in one invocation on one runner — the gate record carries one invocation stamp spanning both runs, and a split record fails, mirroring the acquisition-count pattern; an undeclared path that passed at baseline and is absent at HEAD fails the delta — the join fails closed rather than dropping the vanished test — and otherwise no test failing at HEAD that passed at baseline; pre-existing failures neither block the fix nor excuse a regression, so two standing failures cannot deadlock each other's fixes. The flake-resistance repetition policy covers the pin runs and the suite delta alike; its number and per-test aggregation rule are the phase-1c authoring items; aggregation is at the declared-set grain — every run's observed kind a member of the finding's declared set — and the delta fails closed: a test that passed at baseline and aggregates flaky at HEAD fails the delta (operator ruling 2026-07-21). The pin test pins the defective behavior through the surface that exists at the baseline — that is what distinguishes a defect pin from a feature test. A valid red is a run-time failure of an executed pin: the named test built, was collected, ran, and failed (a kind from the versioned failure-kind enumeration). A pin that fails to build or be collected against the baseline — whatever the diagnostic kind: unresolved identifiers, signature or arity mismatches, trait-bound failures, macro expansion — is not a demonstration and does not satisfy the gate; compile failure counts as red only when the finding declares the defect itself to be that the code under test fails to compile, and that declaration carries validator approval — both no-runtime-pin paths, the compile-defect declaration and the surface-limitation, meet the same bar, so relabeling between them buys no escape from the validator. A defect whose pin cannot be expressed against the baseline surface is a surface-limitation, recorded on the finding issue with validator approval — the same clause forward and retrofit, so neither path fabricates a red the topology cannot produce. Red and green are recorded with test identity and failure kind (the failure-kind enumeration ships as versioned data, completed at phase-1c data authoring — abort and not-collected kinds included, and each kind carries its scope, per-test or whole-suite: a whole-suite kind routes to the cannot-run family rather than impersonating a per-test failure, with doctest compile failure the per-test exception the runner reports against the named doctest and build-script failure an enumerated whole-suite kind — operator ruling 2026-07-21); wrong-reason is a mechanical comparison, not a prose judgment: a mismatch of recorded test identity against the finding issue's declaration, or a recorded failure kind outside the declared expected set — membership, not equality, is the kind comparison, and it stays mechanical under kind instability. Where the surface allows no failing test (the filing rule's own clause), the validator-approved surface-limitation record is the evidence — for a defect that breaks the verification surface itself (a build or suite that cannot run), the recorded failing state is the red evidence, carrying validator approval like its two siblings — one bar on all three no-executed-pin forms, because the gate's own run attempt cannot distinguish a broken surface from a compile-defect at workspace scope (both leave the suite unable to run), so approval is the discriminator and relabeling between any of the three buys nothing — with the gate's baseline run attempt kept as an additional mechanical check on the two suite-cannot-run forms — never the surface-limitation, whose suite runs by definition — rejecting the claim outright when the suite in fact runs (the cannot-run predicate's command binding and exit-and-timeout semantics are a phase-1c data-authoring item beside the failure kinds); the fix's reviews follow immediately after landing. A fix that landed ungated is remediated by the retrofit form: the same gate run performed after the fact against the recorded baseline, marked retrofit on the finding issue — a full record where the pin is expressible, the validator-approved surface-limitation where it is not, partial evidence declared as partial, never a fabricated equivalence. The retrofit closes verification debt, not the process breach: the deviation record stands. Tests authored alongside the fix and never shown failing first are the assertion-based transition this gate exists to block, at any scale.

Falsification: any phase transition in the state artifact without its recorded gate evidence surviving an mdatron check; a commit in the governed set (defined in Finding lifecycle in one place) owned by a finding issue with neither a recorded gate-performed red-and-green run against its recorded baseline, nor a validator-approved surface-limitation record, nor a validator-approved, gate-verified broken-surface failing-state record, nor a valid waiver marker (valid only after first publish — a pre-publish waiver marker is itself a flagged condition).

### Finding lifecycle in one place

Finding lifecycle state — classification, routing, closure — lives in crosslink issues only. Review narrative may exist but carries no state.

- Findings are filed in the subject project's tracker; the subject project field is a routing instruction the tooling enforces.
- Filing is evidence-gated: a finding carries checkable evidence at filing time, either a file-and-line citation that mdatron verifies against the working tree as it stands (uncommitted edits count) or a failing test where the surface allows one. A finding citing absent content is rejected at filing. (Amended 2026-07-19 by operator ruling during the mdatron increment: verification basis changed from HEAD to the working tree — the intent is that cited code exists in the agent's reality at action time, and the change removes any git dependency from the check.)
- Every finding names an owner domain and a validator domain that differs from the owner; sanity-check is the validator of last resort. The halves of an adversarial pair — an author-side domain and its cold-reader domain — never share a reviewer session.
- Lifecycle acts use crosslink's typed comments as the single vocabulary: closures are `result` comments carrying the evidence reference, operator rulings are `decision`, routing is `plan`.
- Closure is evidence-graded for resolved findings: a resolving closure references a commit, gate run, or test; otherwise it is invalid. Disposition closures — dismissed, hallucinated, and consolidated into a named survivor (operator amendment 2026-07-19) — close immediately with their disposition recorded; git and tracker history are the audit trail, so closed records need no open placeholder.
- Waivers are enumerable: any waived criterion, deferred obligation, or accepted risk carries a single canonical marker that one search lists completely.
- Tracker objects are cited by lookup handle wherever they are referenced: a repo-qualified issue ID once hub sync has assigned it (`vsdd-cli #15`), the exact issue title before that, milestone names as recorded, and knowledge-page slugs. Records predating crosslink are cited by file path. A reference that cannot be resolved by a crosslink query or a path is a defect the conformance checks flag.
- Defect fixes are increments (operator amendment 2026-07-19; generalized from a single instance by operator direction — the red-gate discipline is established at layer scale on two incidents, and its fix-scale extension carries the same single instance as the rest of the apparatus; a second fix-lane case is the review trigger). The governed set is decidable because the enumeration alone decides membership — the behavior-altering headline is rationale, not a second test: executable source including test source, build and dependency manifests, emitted diagnostics, schemas, and generated-artifact sources. Mechanical passes (formatting, comment-only edits that alter no executed doc-test, renames) are outside the lane only when the commit states the exclusion and carries its unchanged-verification check — the exclusion is claimed-and-verified, never assumed; a manifest edit whose lockfile and build graph are unchanged may state that and is out. A defect is work owned by a finding issue; an increment build is work owned by its layer issue — the distinction is linkage, not judgment. A defect found in code the current layer is itself building is layer work: the finding files at discovery and routes to the layer issue, and the layer's own red gate governs it; the fix lane governs defects in code outside the current layer's build scope — the union of the layer's declared build-dispatch scope manifests (Recorded review dispatch), a recorded file set, not a judgment — and in both cases filing precedes the fix's implementation. One owning finding per fix commit (the one-divergence-per-dispatch rule the upstream harness proves): a commit serving two findings is nonconformant, and symptoms sharing one root cause take the consolidation path — the findings consolidate before the fix: the absorbed findings close with the consolidated disposition (a disposition closure like dismissed and hallucinated, closing immediately with the disposition recorded and the survivor's handle as its reference; consolidated joins the disposition set as draft vocabulary under the maturity lifecycle), and the survivor lists every symptom, names every pin test, and carries the union of the absorbed findings' labels — consolidation can never narrow the composition, so an absorbed security label still summons the security domain; the gate then runs all the survivor's pins. Work in the governed set enters through its owning issue before implementation, never after, and the commit's structured evidence section (the upstream-conventions format this contract already carries) names it, which is the mechanical linkage predicate. The fix inherits the process at fix scale: the red gate (Phase exit by gate); a composition computed by the same function under the same integrity rules, the finding issue's labels entering as the fix-scale analog of declared surfaces — software-engineer with its cold-reader validator at minimum (pair co-activation and validator-differs-from-owner hold at any set size), a security label adding the security domain; the mutation floor on the fix's changed code when the config declares one; the implementation language's supplement by action-time activation; and its reviews as recorded dispatches (Recorded review dispatch) — fix-scale domain reviews are cold-dispatched with manifests carried in the dispatch vehicle's own prompt — execution work on the autonomous side of the split in Recorded review dispatch, preflighted like any autonomous dispatch; the operator's attended act ends at filing and the dispatch invocation, the grant itself, and the fix's implementation and reviews run autonomous — the injection seam is a named upstream capability requirement held with the swarm-fallback open question (kickoff's prompt assembly is the candidate); the mdatron live fire's routed-plan-comment workaround is the interim, and its dependence on the agent choosing to read it is precisely why construction, not convention, is required, and inline review by the implementing session is a named violation, whatever record it narrates (evidence: the mdatron retroactive-verification execution — resolvable now via this tracker's relay, the issue titled "lane r5 operator-relayed: fix-scale review dispatch mechanics unstated — inline review by the orchestrating session"; mdatron-side numbering "#52" is annotation pending that repo's hub sync — ran its retro-reviews inline under hand-coined review-log slugs with dual-home state, three named falsifications by a cooperating session, operator-caught — the first case of the dispatch-layer deviation class, 2026-07-20). Work defensible as routine maintenance is the case this rule exists for: maintenance framing is how increment implementation front-runs increment gates, and front-running converts open design questions into compatibility constraints once artifacts ship (a diagnostic code emitted before the phase owning allocation could ratify it is version-bound thereafter). There is no bypass lane before first publish, and the falsifiers enforce it rather than trusting it: the waiver escape activates at first publish — the same gate that promotes vocabulary, and the promotion act writes the published marker into the state artifact, which is the machine-readable publish-state the falsifiers consult — and before that marker exists a waiver marker in the governed set is itself a flagged condition, so the bootstrap bypass is countable at zero, not policed by prose (the upstream waiver precedent: mandatory reason-owner-review fields, enumeration by one search, non-compliance costs more than compliance). The investigation surface is the pull request's "Dependency approval" section, per crate: why the dependency (the gap it fills, alternatives considered); the Platform-Engineer supply-chain notes (version-pin discipline, signed releases via cosign / sigstore / GPG, maintainer-trust assessment, transitive-dependency audit via `cargo audit` / `pip-audit` / `npm audit`, and a commit-pin-or-semver-range justification); the Security notes (CVE history, a license compatible with the toolkit's own, threat-model considerations); and the Solution-Owner approval — paired with Solution-Owner, Platform-Engineer, and Security co-author trailers on the commit. Every dependency also carries a living investigation record at `docs/dependencies/<crate>.md`, one file per crate; the retroactive baseline is v1.0-gated: every dependency present at the toolkit's v1.0 manifest has a record by that gate, with the undischarged delta named — two records exist today (sha2 and unicode-general-category), and the remainder file with the v1.0 gate or with their own later addition — and each later addition files its record with the pull request. ## Decomposition (phase 1c)

Milestones are independently buildable and independently verifiable; a milestone may depend on an earlier milestone's behavior, never its internals. **Enforcement-spine-first ordering (operator ratification 2026-07-28, vsdd-cli #819), generalizing invariant-first (vsdd-cli #810):** the superseded component-layer ordering (Layers 0–10, ratified 2026-07-19) scattered each mission-critical invariant across three widely-separated layers — its data at Layer 1, its detection query at Layer 2, its blocking gate at Layer 6 — and concentrated all enforcement in the back third, so the tool could not enforce its own construction until the seventh of eleven layers; the whole bootstrap was built in an unenforced window, and the escapes that window admitted are on record (the six-round routing collapse and the phase-compressed rebuild, Layer-3 compliance audit; the design-cycle bypass, vsdd-cli #815). This re-decomposition makes one structural correction and is honest about its bounds: it re-characterizes the built Layers 1–3 as a shared engine, front-loads the enforcement spine as a single genuine vertical slice (Slice 1) that carries its concern from data through detection to a live self-governance guardrail plus a CI backstop (non-suppressible server-side, a landing-block once branch-protection is wired), and keeps the remaining product capabilities as component-cohesive slices (composition, install, gate, lifecycle, dispatch, cost), each binding its own guardrail at its true-dependency layer rather than deferring all enforcement to one gate layer. It is NOT a claim that every slice is a thin single-concern vertical — only Slice 1 is; re-slicing the cohesive pure-function tiers (composition, pricing) or the single gate-command surface by invariant would fragment them for no gain. Invariant-first (#810) is unchanged: it never demands a mechanized gate before its inputs exist; this ordering adds that when an invariant's detection inputs exist, its detection and its available (friction-plus-CI) enforcement land together in one slice, and its tamper-proof enforcement lands when its true-dependency layer and its independent oracle exist.

**The engine (the shared, already-built base every slice builds on).** In plain terms: the code and data that are built once and reused by every slice, and that a slice depends on *through its behavior, never by reaching into its internals*. It is the methodology harness's own base — vsdd being the methodology harness, the layer that harnesses the agent to the VSDD methodology — distinct from crosslink beneath it and the Claude Code runtime harness it runs on. Two kinds of thing:
- **In code:** reading and writing the `.vsdd/state.yaml` file; taking the snapshot (the effectful read of git, the tracker, and state); the pure functions that derive the phase answer and run the integrity checks (including the git-branch-name check); the three output renderings (segment, human, machine); the statusline wiring script; and the terminal-output-safety cleaner.
- **In data:** the versioned data sets that *more than one slice reads* — the state schema, the composition vocabulary, the statusline data set, the allowed branch-name grammar, and the cost calibration and token-budget numbers.

Data sets that only **one** slice reads are that slice's own inputs, not part of the engine (the dispatch preflight members and manifest schema belong to Slice 6; the mutation floor and gate flake-count to Slice 4). The engine-data list above is illustrative, not exhaustive: any versioned set read by more than one slice — the failure-kind enumeration, the mapping schema, and the cannot-run predicate among them — is engine data by the same rule. "The engine's data" below means these shared data sets.

**The guardrail, and the three grades of enforcement it delivers.** A **guardrail** is a control that blocks or warns at the point of an act (the Platform-Engineering term; guardrails come in detective and preventive flavors, which map onto the grades below). It is not one surface but a per-concern family of the repo's own hand-maintained enforcement surfaces (the **self-governance guardrail** — hooks and CI this repo maintains by hand — versus the **adopter guardrail**, the same check packaged into `vsdd init` for an adopter), each firing at the act it governs: git hooks (`.githooks/`, active today via `core.hooksPath=.githooks`) for commit- and push-time invariants; the crosslink session-start and pre-tool hooks (`.claude/`, `.crosslink/`) plus vsdd's own bootstrap validation-at-read for composition, config-shape, and read-gates; the CI workflows (`.github/workflows/mdatron-verify.yml`, `vsdd-test.yml` — renamed from mdatron-test.yml at #824 — and `routing-gate.yml`, the workflows active today) for server-side backstops — the routing, gate, and budget CI legs adding at Slices 1, 4, and 7; and the approve-then-dispatch manifest gate for dispatch acts. A given invariant's guardrail is honestly one of three **grades**, and the contract must not conflate them: **detection** (the query reads real data and reports — `vsdd status` today, exit 0, cannot block); **friction** (a client-side hook that blocks locally but is bypassable — `git commit --no-verify`, `git config --unset core.hooksPath`, hand-editing the hook, or a fresh clone that never wired `core.hooksPath` — so it records a deviation rather than preventing it); and **CI-backed block** (a server-side workflow the committing agent cannot skip, for whatever the workflow can independently verify). Tamper-proof enforcement of a process invariant against an agent that controls the local tracker is beyond all three: the routing edge is an agent-authored `plan` comment (forgeable), a finding can be disposition-closed to dodge the check, and the local tracker is agent-writable, so a local block certifies against the attacker's own state — the contract's Trust boundaries already rule tracker data corroboration-only, never authoritative (scoped to the phase answer). Turning detection into tamper-proof enforcement therefore requires an independent oracle the committing agent cannot author (CI over server-synced state, and the corroboration/adversarial-review instruments) — the tamper-evidence-by-corroboration keystone of the paused agent-first-controls design (vsdd-cli #815); this re-decomposition front-loads detection and the friction+CI grades, and names #815 as the other half that makes the enforcement tamper-proof. To keep the self-governance and adopter surfaces from drifting (the estate's own hollow-shell and thirteen-hand-hooks failure), each guardrail is a thin wrapper over one shared implementation — the block logic lives in the vsdd binary and its data, the git-hook wrapper and the `vsdd init` payload wrapper differ only in wiring, and a conformance check flags divergence between the hand-wired wrapper and the payload's wrapper source.
