## Summary

The toolkit enables and enforces VSDD for projects whose work is executed by AI agents under a human operator's direction. The product is an installed environment: context, constraints, and hooks wired into crosslink's seams, in which following the methodology is the easiest available path and deviation produces immediate, compiler-shaped feedback. The operator's session-start intent expands deterministically because the process is deterministic: the same project state and process spec produce the same next action from any competent cold agent.

Division of labor:
- **crosslink** (chassis): issues, dispatch (swarm), worktrees, gates, sessions, knowledge, and raw usage capture (harvest, context measurement). The contract chain lives here.
- **vsdd** (methodology layer): process spec, phase state, composition, domain prompts, generated agent context, hooks, and the cost ledger with its insight queries. Installed into crosslink's seams (rules, skills, hook config, house style).
- **mdatron** (conformance engine): validates every methodology artifact, including the phase state file and route table, invoked at action time by hooks and at boundary time by gates. Methodology-agnostic per its boundary preamble (see References).
- **operator**: doctrine, scope, priorities, approval, and oracle authorship (acceptance criteria and manual tests). All other decisions belong to the process or the tooling.

## Behavioral contracts

Contracts are referenced by their exact heading names. Each contract states its normative content, then its falsification path, then the evidence that motivated it.

### Deterministic phase answer

"What phase are we in?" has exactly one correct answer, derivable by any cold agent at any time.

- The phase state is a written artifact in the project repo. The draft location is `.vsdd/state.yaml`; the phase-state-location open question decides the final store in Phase 1b. The contract's mechanics below hold for whichever store is chosen. Contents: current layer, current phase, open-findings pointer, last gate result, active composition, and the published marker once the first-publish promotion act writes it (the machine-readable publish-state the fix-lane falsifiers consult; operator amendment 2026-07-19).
- The state advances only at phase boundaries, by the agent, in the same commit as the boundary evidence. mdatron validates the schema and the consistency of state against evidence: a state claiming phase 2b requires a recorded red-gate result for the layer.
- The state rides the chassis session machinery: the phase pointer travels in crosslink session breadcrumbs and is re-injected on resume after compaction; `session start` surfaces phase status with the prior handoff; phase boundaries require handoff notes; each phase execution and each layer is a crosslink milestone, so tracker-side progress and the state corroborate each other and the phase-versus-milestone integrity query is well-defined from phase 1a onward.
- When the tracker is unreachable, the phase answer is computed from the state artifact alone and reported as degraded. Concurrency, mid-phase crash recovery, state-versus-tracker precedence, and bootstrap validation are decision criteria of the phase-state-location open question.

Falsification: two cold sessions given the same repo and tracker state answer differently (a spec defect, chargeable to the spec rather than the agents); a state artifact inconsistent with repo evidence surviving an mdatron check.

Evidence: session entry has depended on prose reconstruction since the suite era; two sessions could disagree about the project's position, and in the June cycles the flow's position was lost entirely (June-cycle records and the operator interview, in References).

### Directive reconciliation

Every mid-flow operator directive is classified before execution. The classifications: phase-4 routing (bind it — file the routing, name the target phase), spec amendment (amend the design doc, then act), recorded override (execute, record via `crosslink intervene`, state where the flow stands and the re-entry path), or increment entry (the work is an increment — a feature entering at phase 1a, or a defect fix entering the fix lane of Finding lifecycle in one place; the classification also states the split side per Recorded review dispatch — for a defect fix, the attended act ends at filing and the dispatch invocation, the grant itself, with implementation and reviews autonomous; for a feature, the design phases it enters run attended, and the split applies at each dispatch thereafter). (Classification set extended by operator amendment 2026-07-19, the defect-fix lane ruling; split side added by the 2026-07-20 attended/autonomous ruling.)

- The classification is stated to the operator at the moment of receipt. The statement includes the inferred scope: whether the operator's words are read as a specific instruction or as instances of a general rule.
- Silent execution of an unclassified directive is a named defect. The operator holds the authority to redirect; the agent holds the duty to say what the redirect does to the flow.
- Reconciliation includes a substrate step drawn from the AI Engineer domain: when a chassis or harness mechanism serves the directive (milestone, session, hook, skill, config), it is named and offered at classification time. The AI Engineer domain also owns the recurrence-to-structure duty: the second occurrence of an operator correction or struggle obliges a proposed mechanization.
- The classification duty is symmetric (operator amendment 2026-07-19): session-originated code-touching work — a defect fix the agent judges routine maintenance — carries the same classification duty as operator directives. Its statement-target is the finding issue: for self-originated work the classification is recorded in the finding issue at filing, before implementation — the filing is the receipt-moment analog, and the scope reading is the governed-set determination (in or out of the lane, stated with the reason). The lane's substance is stated in Finding lifecycle in one place (defect fixes are increments).

Falsification: a directive executed with no classification recorded in the tracker or session record; a recorded classification lacking the scope reading; a recorded increment-entry classification lacking its split-side statement; a directive served by an available chassis mechanism with no mechanism named at classification; a second-occurrence correction with no proposed mechanization; a session-originated change to the governed set (defined in Finding lifecycle in one place) implemented with no recorded classification.

Evidence: the operator issued directives in the June cycles believing them to be phase-4 routing; the agent executed them without classification, the flow was orphaned, and 137 findings accumulated with 82 of them orphaned before the operator noticed. Scope drift has failed in both directions: single utterances became named schema concepts, and illustrative examples were wired as enumerated special cases (June-cycle records and the operator interview, in References).

### Phase exit by gate

A phase closes only when its exit gate passes. Gates are commands; `crosslink swarm gate` runs them, and their results are recorded in the state artifact and the tracker.

- Red Gate, mechanized: phase 2a closes only when the layer's test suite fails against the pre-implementation commit and the failing run is recorded. Phase 2b closes only when the same suite passes at HEAD. The gate performs the checkout and run; agent assertion plays no part.
- Phase 3 closes only at the stop signal (a round producing only hallucinated findings) with all round findings filed. Phase 4 closes only when the unrouted-findings query returns empty.
- Mutation floor: when the review config declares one (the thorough preset does), the mutation kill-ratio on changed code is a standing gate criterion.
- The red gate applies at fix scale (operator amendment 2026-07-19), mechanized like the layer gate: the gate performs the work and agent assertion plays no part. What the mechanism does differs by commit topology, and the gate defines it rather than assuming the layer shape: the finding issue records the baseline commit (for a single-commit fix, the fix commit's parent), names the defect's test(s), and declares the expected failure kinds — a declared set drawn from the enumeration, since a real defect's kind can vary by platform or run order (operator ruling 2026-07-21); the wrong-reason comparison's second operand is a required field, not an inference; the gate checks out the baseline, applies the defect's pin test to it — test application is the defined fix-scale mechanism, since a fix and its test may share a commit — runs the named test(s) in isolation for defect attribution, and requires red there and green at HEAD; the green half is two runs: the named tests in isolation, where green is the symmetric executed pass — the pin built, was collected, ran, and passed; a skipped, ignored, filtered, or not-collected pin is neither red nor green but its own recorded state satisfying neither half — and the standing suite (the repo's declared test command at workspace scope, the same command the chassis's gate resolves; cross-repo consumers are their own repos' gates) as a delta: the suite runs at baseline and HEAD and the gate compares by runner-reported test path, joining through the declared path mapping when the fix must relocate tests (the mapping is stated in the commit's structured evidence section — relocation-as-fix has a lawful lane, since inline test modules rename by construction when modules move; mappings are set-valued between paths vanished at HEAD and paths new at HEAD — splits and merges are lawful forms, a path appears in at most one mapping per side, and every target of a split inherits the dormancy scrutiny, so no split target escapes it (operator ruling 2026-07-21) — and carry validator approval exactly as deletions do — the approval record enumerates every pair and the gate checks the approved set equals the declared set, one recorded act with per-pair content, mechanical at any scale, so routing a deletion through a mapping buys no validator escape, a fresh passing decoy faces the validator who asks what each pair relocates, and a decoy buried in a bulk table is still a row the record names; no new-at-HEAD test may fail, while a skipped or ignored new test is neither pass nor fail per the pin doctrine's own vocabulary, so a genuinely failing relocation cannot slip by unmatched; a genuinely new test added ignored (no baseline history) blocks nothing, but a mapped target that arrives reported-but-non-executing at HEAD is the dormancy of an existing catcher — the scrutinies compose, and the mapping's record carries the disablement declaration for that pair, so relocation buys no escape from dormancy approval (adopted default, overridable at the phase-1c mapping schema: mapping targets are the report set, so a cfg-vanished target — absent from the runner report — cannot be a mapping target, and that relocation degrades to a source-path disablement with the relocation linkage a validator-trust item; a 1c decision for the source set would legalize such targets and retire the degradation); and a test that passed at baseline and is skipped, ignored, or not collected at HEAD is removal-shaped regardless of its path surviving — it takes its declared, validator-approved lane or fails the delta, so an in-place quarantine cannot hide a baseline-passing regression catcher); a fix that removes an obsolete passing test declares the deletion — path and reason, validator-approved — as its lawful form; a fix that leaves a still-valid test dormant (a feature-default flip, a runtime skip) declares the disablement — path, reason, validator approval — the third removal-shaped lane, keyed on intent alone: it covers the dormant test whether its path survives the runner report (a runtime skip) or vanishes from collection (a cfg-gated flip), and the join treats a declared-disabled vanished path as explained; the three lanes partition the removal-shaped set by intent — gone-and-obsolete is deletion, relocated is mapping, dormant-but-valid is disablement — with each affected path assigned exactly one primary lane and one stated mechanical exception: a relocation whose target the runner cannot report takes the disablement lane, because the report is the join's universe; a mapped pair whose target arrives non-executing additionally carries the disablement scrutiny on the same record, an attached approval, never a second lane claim; the gate runs baseline and HEAD in one invocation on one runner — the gate record carries one invocation stamp spanning both runs, and a split record fails, mirroring the acquisition-count pattern; an undeclared path that passed at baseline and is absent at HEAD fails the delta — the join fails closed rather than dropping the vanished test — and otherwise no test failing at HEAD that passed at baseline; pre-existing failures neither block the fix nor excuse a regression, so two standing failures cannot deadlock each other's fixes. The flake-resistance repetition policy covers the pin runs and the suite delta alike; its number and per-test aggregation rule are the phase-1c authoring items; aggregation is at the declared-set grain — every run's observed kind a member of the finding's declared set — and the delta fails closed: a test that passed at baseline and aggregates flaky at HEAD fails the delta (operator ruling 2026-07-21). The pin test pins the defective behavior through the surface that exists at the baseline — that is what distinguishes a defect pin from a feature test. A valid red is a run-time failure of an executed pin: the named test built, was collected, ran, and failed (a kind from the versioned failure-kind enumeration). A pin that fails to build or be collected against the baseline — whatever the diagnostic kind: unresolved identifiers, signature or arity mismatches, trait-bound failures, macro expansion — is not a demonstration and does not satisfy the gate; compile failure counts as red only when the finding declares the defect itself to be that the code under test fails to compile, and that declaration carries validator approval — both no-runtime-pin paths, the compile-defect declaration and the surface-limitation, meet the same bar, so relabeling between them buys no escape from the validator. A defect whose pin cannot be expressed against the baseline surface is a surface-limitation, recorded on the finding issue with validator approval — the same clause forward and retrofit, so neither path fabricates a red the topology cannot produce. Red and green are recorded with test identity and failure kind (the failure-kind enumeration ships as versioned data, completed at phase-1c data authoring — abort and not-collected kinds included, and each kind carries its scope, per-test or whole-suite: a whole-suite kind routes to the cannot-run family rather than impersonating a per-test failure, with doctest compile failure the per-test exception the runner reports against the named doctest and build-script failure an enumerated whole-suite kind — operator ruling 2026-07-21); wrong-reason is a mechanical comparison, not a prose judgment: a mismatch of recorded test identity against the finding issue's declaration, or a recorded failure kind outside the declared expected set — membership, not equality, is the kind comparison, and it stays mechanical under kind instability. Where the surface allows no failing test (the filing rule's own clause), the validator-approved surface-limitation record is the evidence — for a defect that breaks the verification surface itself (a build or suite that cannot run), the recorded failing state is the red evidence, carrying validator approval like its two siblings — one bar on all three no-executed-pin forms, because the gate's own run attempt cannot distinguish a broken surface from a compile-defect at workspace scope (both leave the suite unable to run), so approval is the discriminator and relabeling between any of the three buys nothing — with the gate's baseline run attempt kept as an additional mechanical check on the two suite-cannot-run forms — never the surface-limitation, whose suite runs by definition — rejecting the claim outright when the suite in fact runs (the cannot-run predicate's command binding and exit-and-timeout semantics are a phase-1c data-authoring item beside the failure kinds); the fix's reviews follow immediately after landing. A fix that landed ungated is remediated by the retrofit form: the same gate run performed after the fact against the recorded baseline, marked retrofit on the finding issue — a full record where the pin is expressible, the validator-approved surface-limitation where it is not, partial evidence declared as partial, never a fabricated equivalence. The retrofit closes verification debt, not the process breach: the deviation record stands. Tests authored alongside the fix and never shown failing first are the assertion-based transition this gate exists to block, at any scale.

Falsification: any phase transition in the state artifact without its recorded gate evidence surviving an mdatron check; a commit in the governed set (defined in Finding lifecycle in one place) owned by a finding issue with neither a recorded gate-performed red-and-green run against its recorded baseline, nor a validator-approved surface-limitation record, nor a validator-approved, gate-verified broken-surface failing-state record, nor a valid waiver marker (valid only after first publish — a pre-publish waiver marker is itself a flagged condition).

Evidence: the issue-tracker-cli project's layer-7 Red Gate passed against the pre-implementation base with zero genuinely failing tests, and the tracking issue for the last plan phase carries three closure comments while remaining open — both were assertion-based transitions that a gate would have blocked (see References for both records). At fix scale: the mdatron path-confinement hotfix landed direct-to-main with its test suite authored alongside the fix and never demonstrated failing first (mdatron deviation record, resolvable now via this tracker's relay: the issue titled "Directive: defect-fix lane for code-touching work (from mdatron deviation)" and its trail; mdatron-side numbering "#51" is annotation, its exact-title anchor landing at that repo's hub sync).

### Finding lifecycle in one place

Finding lifecycle state — classification, routing, closure — lives in crosslink issues only. Review narrative may exist but carries no state.

- Findings are filed in the subject project's tracker; the subject project field is a routing instruction the tooling enforces.
- Filing is evidence-gated: a finding carries checkable evidence at filing time, either a file-and-line citation that mdatron verifies against the working tree as it stands (uncommitted edits count) or a failing test where the surface allows one. A finding citing absent content is rejected at filing. (Amended 2026-07-19 by operator ruling during the mdatron increment: verification basis changed from HEAD to the working tree — the intent is that cited code exists in the agent's reality at action time, and the change removes any git dependency from the check.)
- Every finding names an owner domain and a validator domain that differs from the owner; sanity-check is the validator of last resort. The halves of an adversarial pair — an author-side domain and its cold-reader domain — never share a reviewer session.
- Lifecycle acts use crosslink's typed comments as the single vocabulary: closures are `result` comments carrying the evidence reference, operator rulings are `decision`, routing is `plan`.
- Closure is evidence-graded for resolved findings: a resolving closure references a commit, gate run, or test; otherwise it is invalid. Disposition closures — dismissed, hallucinated, and consolidated into a named survivor (operator amendment 2026-07-19) — close immediately with their disposition recorded; git and tracker history are the audit trail, so closed records need no open placeholder.
- Waivers are enumerable: any waived criterion, deferred obligation, or accepted risk carries a single canonical marker that one search lists completely.
- Tracker objects are cited by lookup handle wherever they are referenced: a repo-qualified issue ID once hub sync has assigned it (`vsdd-cli #15`), the exact issue title before that, milestone names as recorded, and knowledge-page slugs. Records predating the chassis are cited by file path. A reference that cannot be resolved by a crosslink query or a path is a defect the conformance checks flag.
- Defect fixes are increments (operator amendment 2026-07-19; generalized from a single instance by operator direction — the red-gate discipline is established at layer scale on two incidents, and its fix-scale extension carries the same single instance as the rest of the apparatus; a second fix-lane case is the review trigger). The governed set is decidable because the enumeration alone decides membership — the behavior-altering headline is rationale, not a second test: executable source including test source, build and dependency manifests, emitted diagnostics, schemas, and generated-artifact sources. Mechanical passes (formatting, comment-only edits that alter no executed doc-test, renames) are outside the lane only when the commit states the exclusion and carries its unchanged-verification check — the exclusion is claimed-and-verified, never assumed; a manifest edit whose lockfile and build graph are unchanged may state that and is out. A defect is work owned by a finding issue; an increment build is work owned by its layer issue — the distinction is linkage, not judgment. A defect found in code the current layer is itself building is layer work: the finding files at discovery and routes to the layer issue, and the layer's own red gate governs it; the fix lane governs defects in code outside the current layer's build scope — the union of the layer's declared build-dispatch scope manifests (Recorded review dispatch), a recorded file set, not a judgment — and in both cases filing precedes the fix's implementation. One owning finding per fix commit (the one-divergence-per-dispatch rule the upstream harness proves): a commit serving two findings is nonconformant, and symptoms sharing one root cause take the consolidation path — the findings consolidate before the fix: the absorbed findings close with the consolidated disposition (a disposition closure like dismissed and hallucinated, closing immediately with the disposition recorded and the survivor's handle as its reference; consolidated joins the disposition set as draft vocabulary under the maturity lifecycle), and the survivor lists every symptom, names every pin test, and carries the union of the absorbed findings' labels — consolidation can never narrow the composition, so an absorbed security label still summons the security domain; the gate then runs all the survivor's pins. Work in the governed set enters through its owning issue before implementation, never after, and the commit's structured evidence section (the upstream-conventions format this contract already carries) names it, which is the mechanical linkage predicate. The fix inherits the process at fix scale: the red gate (Phase exit by gate); a composition computed by the same function under the same integrity rules, the finding issue's labels entering as the fix-scale analog of declared surfaces — software-engineer with its cold-reader validator at minimum (pair co-activation and validator-differs-from-owner hold at any set size), a security label adding the security domain; the mutation floor on the fix's changed code when the config declares one; the implementation language's supplement by action-time activation; and its reviews as recorded dispatches (Recorded review dispatch) — fix-scale domain reviews are cold-dispatched with manifests carried in the dispatch vehicle's own prompt — execution work on the autonomous side of the split in Recorded review dispatch, preflighted like any autonomous dispatch; the operator's attended act ends at filing and the dispatch invocation, the grant itself, and the fix's implementation and reviews run autonomous — the injection seam is a named upstream capability requirement held with the swarm-fallback open question (kickoff's prompt assembly is the candidate); the mdatron live fire's routed-plan-comment workaround is the interim, and its dependence on the agent choosing to read it is precisely why construction, not convention, is required, and inline review by the implementing session is a named violation, whatever record it narrates (evidence: the mdatron retroactive-verification execution — resolvable now via this tracker's relay, the issue titled "lane r5 operator-relayed: fix-scale review dispatch mechanics unstated — inline review by the orchestrating session"; mdatron-side numbering "#52" is annotation pending that repo's hub sync — ran its retro-reviews inline under hand-coined review-log slugs with dual-home state, three named falsifications by a cooperating session, operator-caught — the first case of the dispatch-layer deviation class, 2026-07-20). Work defensible as routine maintenance is the case this rule exists for: maintenance framing is how increment implementation front-runs increment gates, and front-running converts open design questions into compatibility constraints once artifacts ship (a diagnostic code emitted before the phase owning allocation could ratify it is version-bound thereafter). There is no bypass lane before first publish, and the falsifiers enforce it rather than trusting it: the waiver escape activates at first publish — the same gate that promotes vocabulary, and the promotion act writes the published marker into the state artifact, which is the machine-readable publish-state the falsifiers consult — and before that marker exists a waiver marker in the governed set is itself a flagged condition, so the bootstrap bypass is countable at zero, not policed by prose (the upstream waiver precedent: mandatory reason-owner-review fields, enumeration by one search, non-compliance costs more than compliance). The broken-verification-surface clause in Phase exit by gate is the lawful bootstrap path for the fix that restores a suite that cannot run. After first publish, a bypass is a waiver under the canonical marker — loud, annotated, and enumerable with the rest, and both falsifiers honor it from that gate onward.

Falsification: lifecycle state found in a review-log file that differs from the tracker; a resolved-closed finding without an evidence reference, or a disposition closure without its recorded disposition, or a consolidated closure whose survivor reference is absent or resolves to no finding, or a consolidation survivor carrying fewer labels than the union of its absorbed findings' labels; an open finding without an owner; a filed finding whose citation fails working-tree verification; a governed-set commit whose structured evidence section names no owning tracker issue — layer issue for increment builds, pre-implementation finding issue for fixes — and no valid waiver marker (valid only after first publish; a pre-publish waiver marker is itself flagged); a fix commit whose evidence section names one finding while its gate record shows tests for another.

### Deterministic composition

Given the phase, the project's declared surfaces in DESIGN.md, and the project's review config, the active domains and their dispatch shape are computed. At fix scale the finding issue's labels stand in the surfaces position — one function, one integrity-rule set, both scales (operator amendment 2026-07-19). The function's second input is the composition scope, whose domain ships as versioned data: the phase enumeration plus the fix-lane scope value — the fix lane is not a phase and is never called one; declaring the domain keeps every input defined and determinism testable at both scales.

- The review config is a file (`.vsdd/config.yaml`) with layered loading modeled on crosslink's config: shipped presets, then project config, then local overrides. Presets are suggested starting points, each with an associated cost band (a preset's composition yields its priced bill of materials once the pricing function runs over the stamped counts). The operator customizes freely; the customization is a declared, git-tracked, schema-validated input. Fields: active domains, round budget, stop sensitivity, model tiers and effort levels (each settable per lens and per model-running stage of the review loop — its cold multi-lens rounds, its fix passes, and its terminal verify round, the loop's own names (the terminal verify round decides the stop signal and takes the higher default dial; operator confirmation 2026-07-21), with the draft stage sharing the implementing session's dial; mechanized gates run no model and take no dial, a general truth rather than a loop stage; application follows the control surfaces in Cost is knowable — per-lens effort for cold dispatches awaits the dispatch-parameter seam; operator amendment 2026-07-20, effort joins model tier as a managed dial; a preset's cost band prices the static context bill — effort's runtime thinking spend is the ledger's to report, never the band's to imply), mutation floor, cost bands.
- Config integrity rules are validated by mdatron: pair co-activation (activating an author-side domain activates its cold-reader domain), pair separation at dispatch, and validator-differs-from-owner. The per-domain bar holds at any active-set size.
- A mid-cycle config change is an operator directive and receives the directive-reconciliation treatment with a recorded event.
- Identical inputs produce identical compositions. The rules above carry the doctrine; presets are starting points.
- Composition operates at two timescales. Session composition selects domains per phase. Action-time activation binds content to its moment mechanically: every supplement declares its activation trigger as a required field of the supplement artifact class, and the harness surfaces whichever supplements match the task at hand, with a hook backstop when a file is edited before its matching supplement was read. Generality is structural — adding a supplement means content plus trigger, with no harness wiring. The chassis supplement's always-relevant core rides in the generated always-on session context.

Falsification: two sessions computing different compositions from identical inputs; an emitted context artifact differing from its source data; a config violating an integrity rule surviving validation.

Evidence: the composition matrix lived as prose that agents applied from memory; the tier system was cut in practice while reviews ran at unrecorded ad-hoc compositions; the crosslink-usage knowledge sat in a review-time supplement while the operator believed crosslink was in use and no mechanism was positioned to notice (operator interview; June-cycle records).

### Recorded review dispatch

Phase 3 dispatch runs on crosslink swarm. Every dispatch produces a manifest: what was sent, to which reviewer role, containing which inputs by content hash, under which composition, at which model tier and effort level (operator amendment 2026-07-20), what came back, and where findings were filed.

- Reviewer roles are tool-restricted; a critic role cannot edit. Operator approval — ratification, gates, waivers, the consent grant — never belongs to an agent; a validator's approval record is a different act, distinguished by the 2026-07-20 amendment: the second-domain review judgment Finding lifecycle in one place requires, agent-executable on the autonomous side, signed by its domain identity. A domain prompt is criteria content; a reviewer role is the tool-restricted agent identity that receives domain prompts at dispatch — the two are distinct, and pairing constraints bind domains while session constraints bind roles.
- Dispatch manifests and filed findings are signed with crosslink agent identities, which both repos already carry. Who found what, under which dispatch, is then a verifiable record. Identities are approved before dispatch — approve-then-dispatch, or a pre-approved identity pool — so an agent's earliest tracker write never races its trust approval (operator amendment 2026-07-20; the mdatron kickoff live fire hit the race).
- Design is attended; execution is autonomous (operator ruling 2026-07-20, from the mdatron kickoff live fire; the chassis and the Thermite harness both already build this split — the dive is on the knowledge page cited in References). Design work — spec authoring, review-loop triage, amendment and ratification acts, decomposition — runs in attended, highly interactive sessions: the operator is present, and the session's own subagent fan-outs run under its permission flow, so context-cold lenses inside a design session are attended by construction, their consent surfaced to the operator, never answered for them. Execution work — the installed process's builds, its cold review rounds, its fix-lane dispatches — runs autonomous: detached, container-backed, launched so that no consent surface needs answering mid-run, with the chassis hooks as the policy layer inside the isolation. The mode is never chosen at dispatch: it derives from which side of the split the work is on — dispatch-by-construction extended to the vehicle. A detached execution dispatch on an attended-shaped vehicle — a local session with nobody attached — is the live fire's named defect, not a lawful middle: its three agents idled to timeout, doing nothing, indistinguishable from clean from the outside. Cold remains what the Convergence test's independence clause states — no shared conversation state or memory — and is orthogonal to the split: design sessions dispatch context-cold lenses attended; the built process runs them autonomous.
- Dispatch preflight: before any autonomous dispatch, the substrate checks pass. The check is three-valued — pass, fail, inconclusive — and fail-closed: a check that cannot determine its answer blocks like a failure, never passes silently (the upstream three-valued-exit discipline: an environment failure is never collapsed to a pass). The members ship as versioned data authored at phase-1c data authoring — container runtime with its daemon, consent state, identity approval before launch (the pre-approved pool or the per-dispatch approval act, with key material provisioned into the launch environment either way), model credentials in the launch environment, and project-server trust and load state (the silent-non-load degradation Trust boundaries names, bound here) — each member carrying its observation binding, how the check learns the answer; a failed or inconclusive preflight blocks dispatch naming the member. Environment provisioning is a precondition, not a runtime step, and its acts are the operator's, performed once before dispatch. The dispatch record names the operator act that invoked it — invocation provenance is recorded, not assumed, so the consent-grant-is-the-dispatch-act rule has an instrument rather than a convention. The vehicle's working tree carries the payload half by construction — the vehicle's install step runs inside it, the container path's install-inside as the model — and the preflight's resolution checks run against the vehicle's tree, not the host's, so a vehicle born hollow fails preflight rather than launching silent. During bootstrap the preflight is format-carried like parity: an autonomous dispatch records its substrate checks as a hand-performed checklist on the dispatch record until the preflight command ships.
- A dispatched agent that never started is dispatch-failed — a distinct, loud state, never a clean round — and its instruments are the chassis's, consumed rather than reinvented: the launch-status record written before the launch act, session records, and heartbeat staleness — the last also making started-then-stalled the same loud class. The state has two signatures, both dispatch-failed: the record present with no session activity following (the agent never started), and the record itself absent (the launcher died before its pre-launch write — absence is the launcher-failure signature, never limbo, precisely because the write precedes the launch act). Classification is fenced: a first write landing after a dispatch's dead classification joins as a flagged late-writer under the closed dispatch, never a silent revival — the fencing rule's semantics ship with the preflight data. Tracker-event counting is not the instrument: a clean review files nothing, per the coverage clause, so counting filings can never distinguish it from a dead agent — the chassis records make the distinction.
- Unresolved design questions reaching an autonomous run produce a blocker record on the owning issue and work proceeds on the unblocked parts — escalate, never guess, never stall silently (the upstream kickoff conduct).
- Build dispatches carry scope manifests on the same pattern: a pre-declared writable file set per task. An off-manifest write blocks with a manifest-expansion request. One concern per manifest keeps commits revertible.
- Coverage is declared: the dispatch manifest records which domains did not run and why (no matching surface, declined by config, or deferred with a trigger). Absence of findings and absence of looking are distinguishable facts, and neither produces tracker issues.
- Round stop rules follow the VSDD whitepaper: continue on any real finding; stop when a round is entirely hallucinated; rounds past the stop signal require named new evidence.
- The review budget follows the evidence: cold review concentrates on code-shaped artifacts; prose artifacts get the operator's read and external cold readers; spec-stage structural review — small, early, few lenses — is a first-class use of cold review.

Falsification: a Phase 3 record without a manifest; findings whose provenance traces to no dispatch; a build commit touching files outside its declared manifest; a domain that neither ran nor recorded a reason; an unsigned manifest or finding where signing is configured; a tracker write signed by an identity whose approval postdates the write; a dispatch manifest missing its recorded model tier or effort level; an execution dispatch on a detached vehicle with neither an attached operator nor the autonomous substrate — the live fire's shape; an autonomous dispatch with no preflight record; a preflight record whose inconclusive result was treated as a pass; an autonomous run reopening a recorded operator ruling with no directive-reconciliation record; an autonomous run's artifact resolving an open design question with no blocker record; an autonomous dispatch whose record traces to no operator act.

### Conformance at action time

mdatron validates methodology artifacts — the state artifact, DESIGN.md structure, the route table, domain prompts, generated context — with rustc-shaped diagnostics, invoked by hooks at action time and by gates at boundary time.

- Spec drift is checked mechanically: design docs pin a content hash over the files they govern, and a governed-file change without a re-pin fails the gate (Thermite's doc-drift check, generalized).
- Session entry is enforced: edits to governed files are blocked until the session has read the governing docs (Thermite's spec-discipline hook, generalized), configured per project.
- Vocabulary and register are governed. A register spec (modeled on Thermite's tone-and-voice document: concrete named anti-patterns, with the rationale that agents anchor on the register they read, so corpus tics reproduce) pairs with the vocabulary registry (see References for its location, current and planned). Term additions carry earned-by-recurrence justification. mdatron checks the mechanical subset at action time: invented label schemes, unregistered abbreviations, new-coinage detection, and the listed register anti-patterns.
- Vocabulary and schemas have a maturity lifecycle. Draft terms and schemas may be renamed or deleted freely, carry zero compatibility obligation, and are exempt from strict consistency checks and findings. Promotion to established is an explicit operator act, gated at first publish, and never agent-initiated. An utterance is a concept only after registration: agents do not reify casual operator phrasing into named terms, frontmatter fields, error codes, or schema elements. Forward-only discipline applies to established artifacts only.
- The artifact set is closed-world: the route table is an allowlist, and an unrouted artifact blocks (Thermite's no-route rule, generalized). New artifact classes and new name slugs are registration acts under the same maturity gate as vocabulary. Generated artifacts carry computed names derived from their manifest; agents never hand-name what the tooling can name. Branch names are the same class (operator amendment 2026-07-20): one canonical branch grammar ships as registered data declaring both forms — the vehicle's session-scoped form before hub sync, the display-ID form once sync has assigned one (provisional local IDs never enter branch names; they are the unstable key this design already forbids) — and the enforcement seam is named, since a git ref has no file-admission event: a process-integrity query in Status over this clone's own branches — local refs and their remote-tracking counterparts; other actors' refs are their own repos' concern — reports off-grammar names, with a pre-push hook backstop. Both registered forms are perpetually valid — the standing query checks membership in either, which is decidable from the ref alone, while the pre-push hook checks the same membership and warns toward the currently-preferred form — it never blocks a registered form, so no push is rejected and no retroactive rename is ever forced; hub sync never retroactively obligates a rename, and a session-form branch is never reported merely because sync later assigned display IDs. The live-fire case where one repo accumulated two grammars because the convention existed only as archaeology over upstream source is the motivating evidence (recorded on this tracker: the issue titled "lane r5 operator-relayed: branch grammar is archaeology, not registered data" and the defect-fix lane directive record's observation trail; source records in References).
- Enforcement logic lives in mdatron pattern and registry data. Hook scripts stay thin wrappers; a new defect class is closed by adding a pattern, which is a diffable artifact under the maturity gate.
- Chassis affordances are the default vehicle (operator amendment 2026-07-20, from the affordance-gap audit): every methodology act with a chassis workflow rides it — design authoring the chassis design workflow, spec-to-build the read-only gap analysis, autonomous execution the container kickoff, phase-3 rounds the swarm review (a conditional binding: it activates at the Swarm live fire criterion's pass, whose fallback question holds the alternative — the map records the condition), gates the swarm gate, run monitoring the check surface. Hand-rolling an equivalent while the affordance exists carries a stated reason or is nonconformant — the engineering-conventions divergence rule generalized from conventions to workflows; the condition is decidable at audit against the map and the session records, and the divergence's stated reason is recorded as a directive classification or a decision comment, never loose prose. Where a ridden workflow's conduct conflicts with this contract's discipline, the contract governs — the ride adapts the vehicle, never the methodology, the same precedence as contract-over-primer. The act-to-affordance map ships as versioned data owned by the AI Engineer domain, the same domain whose directive-reconciliation substrate step already names mechanisms per directive — this is that duty at act scale, and the map is the single home for every act-to-vehicle binding: chassis workflows, skills, domain-lens summonings, and session dispatch surfaces alike (operator confirmation 2026-07-21), so an act-scale summoning rule is a map entry, never a second routing surface; the claude-code-cli supplement documents the substrate's summoning mechanics and the chassis supplement its workflow surfaces. Evidence: across two repos and the whole respec's sessions, no chassis workflow was ever self-summoned — the design workflow never ran despite an estate built on design documents, and the estate's one kickoff use was operator-directed and became the live fire; every affordance use traces to an operator instruction, which is precisely the dependence this rule exists to remove.
- The installed environment is a closed world like the artifact set (same amendment): an installed-artifact manifest — versioned data — lists every artifact the environment expects (skills, hooks, servers the substrate config references, rules files, and git hooks) with its source and its lifetime half — tracked wiring or per-clone payload, the two install lifetimes whose divergence produced the hollow shell; git hooks carry the inverted pairing, per-clone wiring in git config over tracked payloads, and the manifest represents both pairings. The substrate config's reference surfaces are themselves an enumerated schema field (project and user settings with their local overlays, project server config and its user-level locals, plugin listings, the statusline command path, git config — the starting list; authored at phase-1c data authoring with the schema). The session-substrate check verifies every reference resolves — three-valued, fail-closed — and its result surfaces in Status's machine and human forms: a wired-but-absent artifact is a loud finding, never a quiet no-op (the segment's field set is closed data and is not grown here; statusline visibility for substrate findings is a phase-1c statusline-data decision). The tracked wiring half fails loud on its own: installed hook wiring is fail-closed, so a missing payload is a nonzero exit surfacing in the substrate rather than a guarded no-op — first-session loudness in a fresh clone rests on the tracked half, which survives the clone by construction (the estate's guard shims are the counter-example: they converted absence to exit 0 for months, and the checker itself is a payload, so nothing else can carry that duty). Additions, the operator's included, enter by the recorded pair — artifact plus manifest entry together: an artifact absent from the manifest is unlisted and flagged; a manifest entry whose artifact is absent is flagged. Distinct from the route table's unrouted, which blocks file admission: a tracked skill is subject to both — the route table governs its content's admission, the manifest its installation — two owners, one artifact, each check naming its own concern.

- Availability is not activation (same amendment): a skill in the substrate's listing loads only by invocation or by the model matching its description — a judgment, not a mechanism. What an act requires in context arrives by one of two reliable paths: injected by hook at the act, or gated on its recorded Read — the upstream read-gate pattern, where the edit blocks until the governing documents' Reads are recorded this session, converting "should have loaded" into "cannot proceed without loading"; Reads are observable events, so summoning becomes auditable. The Read record's guarantee is entry-time, honestly bounded: content evicted by compaction or read partially is a named limit — the recorder notes read ranges, and post-compaction re-entry re-reads — so the gate converts silent non-loading into an auditable record, not into a guarantee of retention. Application — whether loaded content was followed — is audited by instruments that each catch a stated part: the commit evidence sections citing the sources read this iteration (self-report, cross-checked against the recorded Reads), the hook trace log against git history (proves loading preceded the act), the conformance families over outputs (mechanically codified guidance only) — and for judgment-shaped guidance, the cold domain review receiving the same supplement slice, the one instrument that catches read-but-ignored; the audit set claims no more than that.
- Artifacts are retrieval-shaped (operator amendment 2026-07-19, formalizing the operator's original two-audiences concept from the suite era): governed artifacts serve the human reader in full and the agent retriever in slices — unique exact-name section anchors, summary-first sections, stable handles, no intra-section forward dependencies — so a targeted question resolves with one search and one section read. ### Cost is knowable

Every methodology operation has a measurable cost, a breakdown, and a baseline, answerable as queries. The canonical questions — is 100k tokens a lot, what makes it up, how much was cached, would a rewrite reduce it — each have a recorded-evidence answer.

- Cost is denominated in native units: tokens by cache class, wall-clock, rate-limit and window consumption, context occupancy. Dollars are a projection of the ledger through a declared billing context. API pay-as-you-go prices the tokens; under subscription auth the binding constraints are usage windows and operator time. The insight layer — waste, repetition, right-sizing, feedback latency, yield — is unit-independent, and the billing lens varies per adopter.
- Static price: every generated context artifact carries its token count at build time, and the pricing function (pure, in the cost crate) emits a priced bill of materials (total, per artifact, cacheable portion) at session start from the composition and the stamped counts, before the spend. CI budget-gates each artifact class. (Amended in phase 1b: pricing is a distinct pure function — the composition function takes no token counts and cannot price; the prior attribution was wrong.)
- Runtime capture consumes existing sources: Claude Code and Agent SDK telemetry, SDK usage results, `crosslink swarm harvest`, and `crosslink context`. Every recorded figure carries capture-source provenance; an agent never reports a cost it did not observe.
- Unit economics: cost per finding, per round, per phase, per layer, recorded in events and the tracker. Calibration bands update from actuals. Dispatch manifests declare the expected band, and the orchestrator compares actuals per result in-cycle.
- The optimization loop treats content rewrites as measured passes: token price down at constant finding yield is the win condition.
- Efficiency advisories are ledger queries the AI Engineer domain owns, surfaced at session boundaries with numbers: repeated searches propose a crosslink knowledge page; repeated reference-corpus reads propose an index or docs server once the ledger shows the repetition pays for it; cost-per-outcome by model tier and effort level by task class proposes tier and effort defaults in the review config (operator amendment 2026-07-20: the dial was operator-noticed mid-cycle, not advisory-recommended — the gap this clause closes). The effort-scaling signals ship as versioned advisory data authored at phase-1c: up-signals — the rework ratio (findings filed against freshly written text in the following round, over fixes landed), cross-lens convergence density on one defect, and a stalled finding series at stable scope; down-signals — repeated clean rounds from a lens, dismissal-heavy yield, and mechanical residue; each computable from the tracker, the manifests, and git history — the audit trail this contract already names — with the rework ratio joining finding citations to fix commits' changed lines and mechanical residue keying on the commit evidence section's exclusion statements; no new capture. The advisory states its attribution grain per auth mode: per-dispatch token usage under API auth; under subscription auth, effort's cost expresses as window and operator-time consumption, attributable per round at best — the grain is declared, never a promise the auth mode cannot keep. Effort application has two control surfaces, stated honestly: the session dial for work the implementing session performs, and a dispatch parameter for cold dispatches — the latter a named upstream capability requirement beside the manifest-injection seam, since a prompt cannot set an API thinking budget; until that seam lands, a cold dispatch's recorded effort is the vehicle's session-level setting, recorded as such. Advisories follow decision routing — absorbable ones execute, and provisioning or tier defaults reach the operator with the math. Scheduled execution runs on crosslink sentinel. The ledger and events stay legible to crosslink's existing viewers (tui, mission control, web dashboard); vsdd builds no viewer.

Falsification: a cost figure in any record without capture-source provenance; a composition whose price cannot be produced; a calibration band with no linked actuals after a completed cycle.

Evidence: suite-era agents fabricated token and dollar figures because measurement was operator-only; the calibration bands were authored once and never updated from actuals; this session re-derived reference material that recorded usage would have flagged for reuse (suite claude-code-contract records; operator interview).

### The operator authors the oracle

Acceptance criteria, manual test checklists, and approval are operator-authored. No agent authors the oracle it is judged against, and no agent self-certifies a gate.

- Manual director testing is a first-class verification surface with its own checklist artifact per layer.
- Criteria and manual-test items carry provenance; agent-drafted candidates exist only as proposals until operator adoption is recorded.
- The operator's slots are the attended half of the split stated in Recorded review dispatch (operator amendment 2026-07-20): oracle authorship; ratification and phase-gate declarations; waiver review; the consent grant that launches autonomous execution — the grant is the operator's dispatch act itself, the invocation, not a config state an orchestrator could arrange (the chassis's trust design states it: the driver explicitly invoked the dispatch, so trust is implicit); and spec-intent review — whether the contract is the property the operator wanted, the one judgment no instrument closes (the Thermite harness names the same residue). These are acts between autonomous runs, never attachments to them: design sessions and triage are where the operator lives; execution runs unattended and returns records.

## Requirements

Each requirement is referenced by its leading name.

- **Install** — `vsdd init` installs the environment into a crosslink-initialized repo: state artifact, hooks, generated skills and domain prompts, route table stub, gate configs, review config. Idempotent; refuses drifted managed files (extending existing init.rs behavior). Statusline wiring is offered, never imposed: when the substrate settings carry no statusLine entry, init installs the default wiring on operator confirmation — the write is read-modify-write, never overwrite: it adds the statusLine entry and preserves every co-resident key the adopter's file carries, since a crosslink repo's settings normally already hold chassis config — and the confirmation prompt discloses its side effect: it names the settings file it will write, states the default, and names the decline path (a confirmation that hides its write is the interactive-prompt failure mode), and a non-interactive invocation presents no prompt and makes no settings write — the rest of init's installation proceeds unchanged — printing the offer's existence, the manual invocation, the interactive path, and the accept flag — the non-interactive audience reading this output is the flag's audience — never hanging and never writing settings unconfirmed; an explicit accept flag installs the default wiring in a non-interactive run exactly as a confirmed interactive run does (the tool-driven accept path — automation and operators who cannot drive the prompt use the flag, per the upstream CLI convention), and a withdrawn offer overrides the flag — the accept flag never forces a write against a failed probe, and it equals a pre-confirmed offer, so it never fires against an existing statusLine entry either: the refusal conduct holds identically with or without the flag. ## Verification architecture (phase 1b)

Per the phase-1b discipline: purity boundaries, automatable-versus-manual classification, phase-5 candidates, trust boundaries, and the falsifiability instruments.

Pure core (property-test and mutation targets; deterministic, no IO):
- The composition function: (DESIGN.md surfaces — or, at fix scale, the finding issue's labels in the surfaces position — composition scope, review config) to the active domain set and dispatch shape; the composition scope's domain is the phase enumeration plus the fix-lane scope value, shipped as versioned data. - The pricing function (home: the cost crate; its mutation coverage lives under that crate's boundary, now named in the Phase 5 strategy): (generated artifacts with stamped token counts, composition) to the bill of materials. Properties: total equals the sum of parts; cacheable portion bounded by the total; determinism.
- The phase-answer derivation: (state artifact, corroboration snapshot) to the structured phase answer plus the snapshot-scoped part of the process-integrity report. The corroboration snapshot is an explicitly-acquired materialized view — milestone states, round and finding counts, comment handles with resolution status, and the statusline display fields — repo name, session, work item, the active milestone with its open-finding count — precomputed — acquired in the effectful shell; the function is pure over an acquired snapshot and never acquires (the named refinement the phase-1b primer requires for takes-a-clock-shaped inputs). The snapshot schema is audited against the full Status integrity-query list plus the statusline renderer's display fields at phase-1c data authoring, so every snapshot-scoped check's inputs (per-finding owner, validator, and evidence-reference presence included) are materialized fields rather than illustrative ones. Properties: determinism; degraded marking exactly when corroboration is absent or unusable, carried as the degraded kind rather than a bare flag — the absent condition yields the absent kind and the unusable condition the unusable kind, never swapped — so the renderings can name the condition and its versioned next-step text (a present-but-disagreeing snapshot files the integrity finding without degrading, per the phase-state resolution).
- The statusline segment renderer: (structured phase answer; display fields from the corroboration snapshot — repo name, work item, active milestone with its open-finding count; per-field width budgets) to the segment string — the session field stays a snapshot member serving the machine and human forms, no longer a renderer input (operator ruling 2026-07-21). Effectful shell (integration-tested, not proof territory): init deployment and drift refusal (including the statusline offer's settings probe), hook wrappers, tracker and ledger IO, the snapshot acquisition that serves status and its renderings — the segment and human forms alike are renderings over the derivation's output and the snapshot's fields, the segment renderer pure core, the human form rendered in the shell from the same inputs (no second computation on any form — with one enumerated exception: the broken-state branch, where no derivation output exists and the shell composes all three outputs itself — the segment mark, the human diagnostic, and the machine state-unreadable signal), context generation IO, gate command execution.

The cost engine ships as a separate crate in the vsdd workspace with mdatron-style boundary discipline: methodology-agnostic (dimensions are caller-supplied labels), zero vsdd-core imports, versioned public data contracts (ledger entry schema, capture-source provenance enumeration, bill-of-materials format), fronted by `vsdd cost` subcommands. Extraction to a standalone app triggers on a second real consumer: a project outside this methodology adopting it, or upstream crosslink interest in the ledger schema. An absorption proposal to the upstream author is worth making regardless; Thermite's token-economics thesis currently has no measurement layer. Rationale: the engine passes the agnosticism test, but it has one consumer today, and the two-repo record shows coordination cost is real.
