### 1. document set and authority chain

Three documents form an explicit chain, each naming the one above it as its authority:

1. **Audit** (`docs/full-codebase-audit-2026-08-16.md`). Header: "Status: Complete; evidence ledger and cleanup record; Companion plan: docs/production-remediation-design.md; Constraint: No runtime code changes in this audit pass." Section 1 "Audit standard" states the reading rule ("Each file is read and its claims are traced through callers, state, permissions, failure behavior, and user-visible entrypoints") and a fixed per-file record schema (purpose/ownership, reachability, contracts, security boundaries, limits, failure behavior, real-path tests, doc discrepancies, duplicates, action = keep/repair/consolidate/remove mechanism/investigate). Section 2 is a progress ledger by area (206 production Rust files, 234 integration tests, 12 fuzz, 20 scripts, 22 prompt assets, 68 Markdown, 3 binaries - all "Complete"). Section 3 is a validation log of the pre- and post-audit toolchain runs. Section 4 holds cross-path findings; section 5 is file-by-file (`#### path` / `Status: Read` / `Disposition:` / bullets); section 6 is the rule-injector deletion manifest; section 8 is an append-only dated log; section 9 "Completion reconciliation" supersedes stage-local notes ("Because this was maintained as an append-only working ledger, stage-local statements ... record what was unknown at that point ... the completion reconciliation at the end of this document supersedes those progress notes"). Findings are `### F-NNN - title` with `Severity:` (Critical/High/Medium) and `Status: Confirmed ...` lines and a "Required outcome:" paragraph; 143 unique findings (68 Critical, 65 High, 1 conditional, 8 Medium, 1 product decision per sec 9). Section 10 records a user-directed target architecture (rotating planner/worker/VDD verifier) and explicitly says it "is not a claim about current implementation".
2. **Remediation design** (`docs/production-remediation-design.md`). Header: "Status: Complete audit-derived implementation design; update when remediation evidence changes. Owner intent: Repair and prove intended capabilities ... Companion evidence: docs/full-codebase-audit-2026-08-16.md". Sections: 1 Purpose, 2 ten non-negotiable principles plus 2.1 "Current external engineering baseline" (dated citations of Agents SDK, MCP 2026-07-28, SLSA/TUF/Sigstore, Anthropic/OpenAI eval guidance, two arXiv preprints - "comparison baselines, not evidence"), 3 "Definition of operational" (a ten-row requirement/evidence table: reachability, success, failure, security, resource safety, state continuity, observability, evaluation, frontend parity, documentation), 4 target architecture (4.6 rotating planner/worker/verifier), 5 workstreams W0-W28, 6 allowed removal criteria, 7 delivery sequence, 8 release gates, 9 audit-driven amendments (58 dated bullets, each citing audited files and the workstream changed).
3. **Slices** (`docs/remediation-slices/`, README + 108 files). README: "The canonical documents remain the source of findings and architecture; these files are the execution backlog." Invariants ("Backlog integrity"): ids contiguous S-001..S-108; every F-001..F-143 has exactly one primary slice; every W0-W28 has at least one slice; dependency graph acyclic (15 topological layers listed); all slices Small or Medium with explicit acceptance; "Changing ownership, dependencies, or slice count requires rerunning these checks and updating this index in the same change." Every slice has the same header fields (108/108): `Status`, `Effort`, `Primary findings`, `Workstreams`, `Depends on`, `Canonical sources`; and the same four planning sections (`## Outcome`, `## Implementation boundary`, `## Acceptance`, `## Handoff`; 105/108 for the latter three). The `Acceptance` section's third bullet is a template: "Relevant deterministic tests and trace assertions pass; attach an artifact-bound VDD receipt once S-088 is available." The `Handoff` template: "Record changed artifact generations, commands/tests run, typed evidence receipts, unresolved risks, and any newly proposed slice. Completion of this slice does not imply completion of its parent workstream."

How they are amended: the audit was never amended after its commit (single commit 00eb0161). The design was amended once after that (445808b5, 2026-08-22, adding a concurrent-heads paragraph under W5 when S-053's follow-up found the need); its section 9 amendments are all dated 2026-08-16, i.e. written during the audit day itself. Slice docs are amended by appending delivery sections at implementation time (S-001 "Delivered architecture / Reviewed artifact generation / Test skepticism and verification state / Scope and unresolved risks"; S-022 "Delivered architecture / Verification evidence"; S-099 "Completed implementation - 2026-08-28 / Evidence / Residual boundary"; S-033 "Delivered - 2026-08-25 / Verification evidence / Residual boundary" prepended above the planning sections). The README index was amended 5 times after creation (slices S-103..S-108 were added on 2026-08-21 by splitting W5 work: hub finding comment 2026-08-21T16:01 "I split these into S-103/#1074 ... S-104/#1075 ... S-105/#1076"; the PR #66 body still says "102 ... slices", the README says 108).

Decisions are recorded in three places: (a) hub comments of kind `decision` on the slice issue (28 by the driver, plus per-worker ones; e.g. s001-wave seq 2 "S-001 architecture decision: capability maturity is release data, not prose"); (b) an `## Architecture decision` section in 8 slice docs and "The credible alternative was ... It was rejected because ..." paragraphs (S-001); (c) the design's section 9 for anything that changes the plan. Corrections to the maintainer's own prior decisions are also logged as decisions (driver 2026-08-19T23:52 "Correction: the automatic CHANGELOG.md update on issue close is intentional project behavior, not a workflow defect. What keeps them honest (observed mechanisms): the README backlog-integrity contract; `Status` wording that refuses to claim VDD ("this document does not claim local review or ordinary tests are a VDD receipt", S-001; "No such receipt is fabricated", S-099; S-088 "This manual review ... is not represented as an alternate-model VDD pass receipt"); artifact digests in 48/108 slices (SHA-256 of file manifests or `git diff --binary` ranges, e.g. S-007 `sha256:0d3b75a6...`, S-019 `S019-G1`/`S019-G2`, S-099 `S099-G1` "Any change to the listed VDD source or test artifacts invalidates it"); hub issue references in 69/108 slices; the driver's periodic "Reconcile stale remediation slice status documents" issue (2026-08-28, eight docs reconciled "against their closed Crosslink issues and delivered commits"); the generated CHANGELOG lines committed byte-for-byte ("Generated CHANGELOG content was not hand-edited"); and the `capabilities/registry.json` -> generated `docs/binary-capability-matrix.md` projection whose header says "Do not edit this table by hand: prose is not readiness evidence" and in which every route is still `partial` or `unsupported` with "none - not operational" (Registry Generation 4).

### 2. per phase

Mapping is mine; the repository never uses the VSDD phase labels (no "1a", "red gate", "Phase 3" vocabulary anywhere read; the slice sections and hub comment kinds are the native vocabulary).

**1a Behavioral Specification.** Artifact: the `Outcome` + `Implementation boundary` + `Acceptance` sections of each slice, derived from an audit finding's "Required outcome" paragraph and a workstream's bullets (F-085 -> S-022; F-007 -> S-007; "Design requirement (no primary audit finding)" -> S-088). Produced by the maintainer's driving agent in the audit pass (all 102 original slices are in commit 00eb0161 together with the audit and design). Gate: README backlog integrity (exactly-once finding ownership, acyclic deps). Record: the slice file; the design's section 9 when a finding changed the plan. Examples: S-022 Acceptance "A configured blocking gate prevents mutation/final success on failure, absence, parse error, or stale artifact"; S-099 Acceptance "Malformed, contradictory, truncated, missing, out-of-range, duplicate, and empty verdicts return error/inconclusive, never clean". Not observed: Gherkin/BDD scenarios, acceptance-criterion ids at spec time (S-019 later minted `S019-E1..E13` receipts at delivery time, not in the plan).

**1b Verification Architecture.** Artifact: design section 3 "Definition of operational" (ten evidence rows), section 8 release gates, and the slice Acceptance template bullet "deterministic tests and trace assertions ... artifact-bound VDD receipt". Within slices, the `Test skepticism and verification state` / `Test design and skepticism record` sections (S-001, S-004: "The former integration suite accepted applied + skipped + failed == total ... Those assertions were removed. Replacement tests require terminal Writable or RecoveryRequired states and inspect real end state"). Produced by the driver or worker at implementation time. Gate: none mechanical beyond CI. Record: slice doc. Not observed: a separate verification-architecture document per slice before implementation.

**1c Spec Review Gate (decomposition).** Artifact: the slice backlog itself (108 Small/Medium units, "If a slice grows beyond medium, split it before implementation"), plus pre-wave lane audits (hub issue "Audit remediation backlog for safe parallel execution lanes", 2026-08-20: "Strictly dependency-free planned slices are S-001, S-002, S-004, and S-005 ... Hold S-002 for isolated/sequential integration because it changes repository artifacts ... likely to conflict broadly"; "Plan next parallel remediation wave" 2026-08-30: "Dominant source surfaces are disjoint ... Defer S-079 until after S-083 due input/render overlap; do not parallelize S-039 with S-082"). Produced by the driver as a `result` comment before each wave. Gate: README invariants; "Select a slice whose listed dependencies are Verified" (README step 1) - observed to be relaxed: "If delivered-but-pre-VDD dependencies are provisionally accepted, 20 more slices become dependency-ready ... but the ledger formally requires Verified predecessors and none use that status yet" (same audit comment), and in practice no slice ever reached `Verified` (sec 7). Not observed: a multi-domain spec review (no security/UX/etc. reviewer roles; the only reviewer identity is the orchestrator or "independent fresh-context review").

**2a Test Suite Generation (red gate).** Not observed as a phase. Tests are written with the implementation in the same commit (S-001 commit d8a8898f: `src/capability_evidence.rs` + `tests/capability_evidence_e2e.rs` + data files, 13 files). No commit, slice section or hub comment records a failing-first run; the S-007 receipt lists `cargo check/clippy/fmt/targeted suites` all "Passed" with no red step. Adversarial tests are described post hoc ("The replacement integration suite executes nine isolated trials ... It also rejects altered corpus-review digests, self-review identity, relabeled/tampered traces ...", S-001).

**2b Minimal Implementation.** Artifact: one signed implementation commit per slice (conventional subject, e.g. `fix(migrations): fail closed at startup` 8676953f for S-004; `feat(guardrails): enforce diff and quality gates` 5753404b for S-022). Produced by (i) the driver agent itself for most slices (hub: S-012..S-057 threads are driver-only), or (ii) a wave worker that edits code only, with the driver integrating (sec 3). Gate: crosslink `work-check.py` PreToolUse hook blocks Write/Edit/Bash without an active issue (72 `intervention` records, mostly "Blocked: no active issue"); `git commit` is a gated command (`.crosslink/hook-config.json` `gated_git_commands`); CI on the draft PR. Record: hub `result` comment carrying commit hash, signature, files, digests (s004-wave seq 12: "commit=8676953f...; files=9_scoped_only; status=clean; hook_cargo=false; ... push=false"). The "Keep adjacent cleanup out of this change" boundary bullet appears in every slice; scope creep is handled by minting a new slice or issue ("Create a new slice for discovered work rather than silently expanding scope", README; the W5 split into S-103..S-105).

**2c Refactor.** Not observed as a separate step. Clippy-driven mechanical fixes are recorded inside the verification record ("strict Clippy initial FAIL exactly 3 (needless_borrow, match_like_matches_macro, collapsible_str_replace), mechanical corrections applied, strict rerun PASS", s001-wave seq 5). Commits typed `refactor(...)` exist (S-005 `refactor(config): add typed environment registry`) but denote the slice's nature, not a post-green refactor pass.

**3 Adversarial Refinement.** Two distinct things carry this name here. (a) "Adversarially reviewed" in a Status line = an independent fresh-context review by the orchestrator (or a worker's "primary skeptical code/test review") that returned `changes required` at least once and was re-run to pass: S-001 "The first independent review returned changes required: effect IDs were self-asserted rather than observed, trace hashes omitted scenario/schema ... Those implementation defects were corrected, and the mandatory independent re-review passed"; S-007 "Independent fresh-context review: Passed after two caught-and-fixed gaps"; hub kind `review` comment s001-wave seq 3 "Independent quality review PASS by primary-orchestrator-6vw9 ... Reviewed dimensions: final-environment graders, success/failure coverage, multi-trial design, trace assertions, effect-observation assertions, artifact bounds/isolation". (b) "VDD" = the product's own alternate-model verifier (S-088, S-099..S-102), which the design requires as the slice verifier but which did not exist until 2026-08-27 and was then bootstrapped by a manual review ("Bootstrap manual review of canonical VDD verifier", hub 2026-08-27T22:21: "Architecture verdict: CHANGES REQUIRED. QA verdict: CHANGES REQUIRED" with five findings filed as #1183-#1187 and repaired in 5f014cbf). No slice records an alternate-model VDD receipt against its artifact (the phrase "VDD receipt" appears in 105/108 files, mostly via the acceptance template; 69 status lines explicitly defer VDD; the other 39 say Complete/verified/implemented without claiming one; none records a VDD pass receipt; see sec 7). Gate: none mechanical; the Status wording is the gate. Record: slice `Review findings resolved` / `Adversarial review corrections` sections (4 files), hub `review`/`finding`/`observation` comments.

**4 Feedback Integration.** Artifact: follow-up issues created from review findings and full-suite failures, each closed by its own commit with its own generated CHANGELOG line (hub: #1183-#1187 from the S-088 review; #1055 worktree fixture defect carried as an explicit exception across many slices: "The six #1055 failures were ... so this slice did not edit worktree or sandbox code", S-001). Driver `finding` comments (4) and `blocker` comments (3) name root causes ("Repair category: local correctness/test isolation", 2026-08-25). Record: hub issue + commit + CHANGELOG line; slice `Unresolved risks and queues` sections (8 files). Example: S-019's hosted CI failure produced generation `S019-G2` ("fixes both causes rather than weakening the probe") and "Hosted confirmation of S019-G2 is intentionally recorded on Crosslink issue #1027 after publication rather than predicted in this artifact receipt."

**5 Formal Hardening.** Partially observed as fuzzing and digest binding rather than formal methods: S-003 made the nine fuzz targets hermetic and unit-testable; CI runs `cargo test --manifest-path fuzz/Cargo.toml --lib`; W28/S-099 require "fuzz the entire parser/triage boundary". Artifact digests (sec 1) serve as the invalidation mechanism ("any artifact change invalidates that queued generation", S-019). Not observed: property-based proofs, model checking, formal specs.

**6 Convergence.** Not observed at slice level: the README's `Verified` status was never reached by any slice; the arc converged administratively (PR #66 merged 2026-08-31 with 191 commits, 697 files, +289,929/-71,878) while 69 slice status lines still defer VDD and none records a receipt. At program level the driver produced progress audits ("15/102 (14.7%) are implementation-delivered ... 31/143 (21.7%) primary findings", 2026-08-20; "the strict feature-repair arc has four remaining VDD slices in an authoritative dependency chain: S-099, then S-100 and S-101 in parallel, then S-102", 2026-08-28). Release gates (design sec 8) remain unmet by the registry's own data (every route non-operational).

### 3. roles and dispatch shape

Roles observed:
- **Driver/orchestrator** = hub agent `6Vw9` (also self-named "primary-orchestrator-6vw9", "parent", "root"). Created 243 of the 247 issues in the window, wrote 1,361 comments, holds the only heartbeat. It audits, plans waves, implements most slices alone, reviews worker diffs, runs all Cargo gates, commits (signed), closes issues, and cannot push (sec 6).
- **Wave workers** = short-lived hub agents, one per slice, in isolated git worktrees. Two generations of naming: first wave `s001-wave`, `s004-wave`, `s005-wave` (2026-08-20); later `wave1-s059-sol`, `wave1-s062-sol`, `wave1-s086-sol` (2026-08-27, the "-sol" suffix matching the "GPT-5.6 Sol xhigh" model named in the plan comment), random ids `xdNo`/`Xnwv`/`NeZq` for wave two (S-087/S-091/S-094), then `s090-wave5`, `s093-wave5`, `s097-wave5` and `s060-wave6`, `s061-wave6`, `s098-wave6` (2026-08-30). Waves three (S-063/S-081/S-088) and four (S-084/S-085/S-095) and the S-076/S-077/S-083 wave left no worker refs; their plans say workers were "forbidden from tests/builds/runners/docs/Git/Crosslink" (Codex workers), so only the driver wrote hub events (inferred from absence).
- **Independent reviewer** = the orchestrator in a "fresh context" (S-007 "Independent fresh-context review"; S-001 "Independent reviewer primary-orchestrator-6vw9"). No second human or second model identity is recorded for reviews.
- **Human maintainer** = owns the push and merges (the three `blocker` comments: "Repository policy permanently forbids the agent from performing the sole remaining push, so external human action is required"), removes stuck worktrees ("Parent verification resumed after human removed stale test worktrees"), and issues corrections ("User correction supersedes the issue's original mixed-toolchain wording: Rust 1.98.0 is now the sole ... toolchain").
- **Verifier (VDD)** = a product role, never exercised against a slice in this window (sec 2 phase 3).

Wave pattern (observed from hub plans and worker refs):
- Width: three workers per wave, every time (first wave S-001/S-004/S-005; wave one S-059/S-062/S-086; two S-087/S-091/S-094; three S-063/S-081/S-088; four S-084/S-085/S-095; S-099 alone then S-100+S-101 then S-102; five S-090/S-093/S-097; six S-060/S-061/S-098; then S-076/S-077/S-083). Selection rule: dependency-ready and "low-overlap"/"disjoint source surfaces", chosen by a pre-wave audit comment.
- Worker contract changed between the first wave and later waves. First wave workers ran focused Cargo gates themselves under a "serialized Cargo queue" granted by the coordinator ("The remediation-wave coordinator granted a serialized Cargo queue", S-005; "CARGO_BUILD_JOBS=1 and test-threads=1 throughout; queue released", s001-wave) and recorded a full result receipt and commit. A "Wave incident" decision (2026-08-20T22:32) records that a Codex plugin cache hook launched implicit repository-wide Clippy inside a worker and "All workers were interrupted". From wave one onward workers are **code-only**: "Each ... worker writes production code and focused tests only - no Cargo, builds, tests, Clippy, fmt, runners, Git commits, or cleanup. Parent 6Vw9 will inspect every diff, reconcile overlaps, run Rust 1.98 resource-bounded verification serially, fix concrete failures, commit, and monitor exact-head CI" (wave two plan). Worker `handoff` comments are correspondingly thin ("S-059 production code edits finished for parent review; no build, tests, formatting, commit, or verification run by worker"; wave five: "Code-only S-093 handoff completed. Root retained caller/session isolation, removed decorative cancellation and unsafe loop lifecycle changes ... no worker verification claim retained").
- Manifests: none as files. Each wave is a hub coordination issue ("Coordinate incomplete-feature repair wave N") whose `plan` comment names the slices, their child issue ids, the model/effort, the prohibitions and the parent's duties; each child slice issue is labelled `remediation` and created by the driver immediately before dispatch (e.g. #1167/#1168/#1169 at 2026-08-27T11:24-25).
- Ceilings observed: three agents; `CARGO_BUILD_JOBS=1` then 4 after the toolchain correction; `--test-threads=1` everywhere; zram swap reset before dispatch ("Reset saturated zram swap to active 8 GiB with 0 used before dispatch"); worker lock per issue (`LockClaimed`/`LockReleased`, `auto_steal_stale_locks: false`).
- Fan-in: one integration commit per wave by the driver (`feat(agent): complete first feature-repair wave (#1071)` 399a19e9; `feat(agent): complete wave-two lifecycle wiring` 7b378a66 "Refs #1166 #1167 #1168 #1169 #1170 #1171"; `feat(agent): activate plugins keybindings and canonical VDD` 49ffbdbc). The first wave instead used three per-slice commits plus `merge: integrate S-00N ...` merge commits (9f80ae77, fe92796b, 870cd36d).

### 4. review conduct

What "adversarially reviewed" meant: a single independent pass by the orchestrator in a fresh context over the exact diff and tests, with a written `changes required`/`pass` verdict, followed by mandatory re-review after corrections. Evidence of real teeth: S-001's first review failed on four substantive points (self-asserted effect ids, trace-hash scope, unbounded artifacts, non-independent review identity); S-007's review caught a stale positive assertion and a wrong argument-key convention; the S-088 bootstrap review returned CHANGES REQUIRED with two HIGH, two MEDIUM and one HIGH validation-gap finding, each with file:line citations, each filed as its own hub issue (#1183-#1187) and repaired in a separate commit (5f014cbf) before S-088's status moved to "bootstrap manual review and repair complete". Review dimensions are enumerated in the receipt (S-001: six dimensions). The reviewer is explicitly forbidden from editing ("make no implementation edits; record concrete severity-ranked findings and a ready or changes-required verdict", bootstrap plan).

Rounds and stop rules: no fixed round count is written down. Observed pattern is review -> corrections -> one re-review -> pass; no slice records more than two review rounds. Stop rule for the program's VDD chain was written once ("Do not launch S-102 until both close, and do not pad the wave with unrelated cleanup").

Deterministic gates precede review (design 4.6 "checked first by deterministic acceptance gates and then ... by a fresh VDD verifier run"); in practice the gate list is the same everywhere: `cargo fmt --check`, `cargo check --locked --all-targets --all-features`, strict Clippy `-D warnings`, full serialized test suite, Windows GNU cross-check, `git diff --check`, repository hygiene script + 27 policy tests, cargo-deny; later also fuzz check/Clippy/tests. These are recorded as a `### Cargo command record` table (S-001), a `| Gate | Result |` table (S-007) or bullet list (S-022, S-099).

"Deterministically verified" (Status of 30+ slices) = those gates passed and were recorded, no independent review claimed. "Implemented and verified (2026-08-30)" (S-060 etc.) = same plus the wave integration commit's full-suite run.

VDD receipts: defined by S-088 (`CanonicalVddRequest` binds assignment, objective/acceptance digests, artifact generation, source receipts, deterministic check receipts, worker model identity; output `pass`/`fail`/`inconclusive`/`verifier_error`, "Receipts are permanently ProposedOnly" until S-100/S-102). Gated by: alternate provider/endpoint/model-family separation with no silent fallback, unchanged artifact generation, strict JSON schema v2 (S-099), blocking finalization (S-100), bounded transport (S-101), transactional evidence + issue promotion (S-102). S-088 itself "cannot bootstrap trust by verifying itself" (README) and so was gated by the manual review. An "Interim typed receipt" YAML (S-007) with `vdd: verdict: not_run, queue_state: retrospective_pending_s_088` is the pre-S-088 stand-in. After S-088/S-102 landed (2026-08-27/28), 69 slice status lines still record VDD as pending and none records a receipt; the "retrospective VDD queue" promised in S-007/S-019 was never drained in the record (sec 9).

Findings filing/closing: a review finding becomes a hub issue immediately (title = imperative sentence, label `remediation`, `related` link to the parent), is fixed in a dedicated commit, closed with a `result` comment, and the crosslink close event appends a CHANGELOG line that is then committed byte-for-byte in a `docs(changelog): record ...` commit. 260 closes in 13 days.

### 5. records discipline

Commit messages: 201/205 subjects in the window use a conventional prefix `type(scope): imperative` (`feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`, `build`, `merge`); 41 subjects name a slice; 12 end with a crosslink id in parentheses `(#1156)`; bodies are one paragraph of what/why with occasional `Refs #...` (1) or `Closes S-102 (#1199)` (1). No Co-Authored-By except one, no Signed-off-by. Commits are SSH-signed and the signature verification is itself recorded in the hub result ("signature=verified SSH ... key SHA256:..."). The one exception is the audit commit 00eb0161 whose message is the bare sentence "audit agent architecture and remove legacy rule injector" (182 files, unsigned). Two-commit cadence per slice: implementation commit, then `docs(changelog): record S-0NN completion` (65 of the 205 commits are changelog commits).

PR bodies: PR #66 (the whole arc) uses `## What changed` / `## Why` / `## User-visible impact` with slice ids inline; PR #61 uses `## Summary` / `## Security impact` / `## Validation` (exact commands) / `## Dependency constraints`; PR #71 uses `## Scope` / `## Integrity constraints` / `## Verification so far` / `## Current blocker` (citing a hub issue). ### 8. divergences from the whitepaper, and practices it does not mention

Divergences (relative to the phase list given to me; inferred where the whitepaper's exact wording was not re-read):
- No red gate: tests and implementation land together; no slice or commit shows a failing-first run.
- No multi-domain spec review: review is one role (the orchestrator in a fresh context) with ad-hoc dimensions; no accessibility/privacy/UX/etc. domains; the S-088 bootstrap review split into "Architecture verdict" and "QA verdict" only.
- Adversarial refinement by an alternate model (VDD) is designed and built but not applied to the slices; no status line claims it and 69 defer it explicitly; the product's own verifier was the deliverable rather than the method's instrument. The method's roast is replaced by self-review with written verdicts and digests.
- Convergence/exit signal never fires; the arc ends with a merge while the backlog's own vocabulary says nothing is Verified; `Verified`, `Planned`, `Ready`, `Blocked` are unused in files.
- Phase labels are absent; the native vocabulary is slice sections and hub comment kinds.
- Spec amendments are near-zero after day one; the whitepaper's feedback-into-spec loop shows up as new slices and hub issues instead of edits to the audit/design.

Practices the whitepaper (as summarised to me) does not mention:
- Artifact-generation digests as receipts (SHA-256 over sorted manifests or `git diff --binary` ranges; receipt invalidated by any mutation; receipts bound to CI run ids on the exact head).
- Separating "deterministic gates", "independent review", and "VDD" as three distinct evidence classes with distinct Status wording, and refusing to upgrade one into another in prose.
- Code-only workers with a verification-owning parent (after the first-wave incident), fixed at three per wave, chosen by a written overlap audit; serialized Cargo with explicit job/thread ceilings and swap resets recorded as part of the receipt.
- Signed commits whose signature verification is itself logged; the push reserved to the human, enforced by hook and recorded as `blocker` comments.
- Machine-generated CHANGELOG lines committed unchanged in dedicated commits; an explicit correction when the maintainer had hand-edited them.
- Issue-gated tool use (no edit without an active hub issue) producing an audit trail of blocked attempts (`intervention`).
- A capability registry with graders and a review record that forbids prose from promoting maturity, and generated user docs that still say "not operational" for every route.
- Audit as a one-shot, append-only ledger whose end-reconciliation supersedes its own earlier notes, plus a dated external-baseline section with citations retrieved on the audit date.
- Keeping failed attempts in the receipt ("These events are retained here so the receipt does not hide failed attempts or substitute targeted results for the full gate", S-007).
